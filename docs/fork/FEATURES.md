# What the fork adds: a log to rebuild it anywhere

Everything this fork does that upstream OpenBot doesn't, written so it can be rebuilt in another app: what Elias gets, why, how it works independent of OpenBot's code, where it lives here, and how to check it. Same format as Codync's `docs/fork/FEATURES.md`.

**Agents: every fork change adds or updates its entry here in the same commit.** Newest last. Build tooling and fixes for this Mac count too.

Skipped features, to pick up later: [LATER.md](LATER.md).

---

## 1. No auto-updates

- **Get:** the app never checks for, downloads or installs an upstream release.
- **Why:** an official release would silently replace the fork's build and every change in this file (Codync lesson, its entry 2).
- **How (portable):** one compile-time switch that the updater's enable condition reads first; keep the upstream updater code so merges stay simple. With the switch off the app uses its own "updates unsupported" path (as for unpacked builds), so no electron-updater module loads.
- **Here:** `updatesAllowed = false` in `src/main/fork.ts`, read as `forkUpdatesAllowed &&` at the top of `updatesEnabled` in `src/main/application-services.ts`. `app-update.yml` still ships (unused).
- **Check:** `grep -n 'forkUpdatesAllowed &&' src/main/application-services.ts`; Settings shows updates as unavailable; no `~/Library/Caches/openbot-updater/pending/update.zip` appears after an upstream release.

## 2. Dock launcher: one click builds `main` if it changed, installs, opens

- **Get:** **OpenBot Launcher** in the Dock (like the Codync, Ghostex, FigCraft and EffectCraft launchers). Click: if `main` has a new commit since the last install, a small window builds it (Stop / close / ⌘Q cancel the whole build), replaces `/Applications/OpenBot.app` and opens it; otherwise it just opens OpenBot. Never quits or replaces a running OpenBot.
- **Why:** Elias's apps all rebuild from `main` this way; agents commit without building, and the next launch builds once.
- **How (portable):** a shell script plus a tiny Swift AppKit window that runs it and shows the log's last line (only dyld's `Reason:` / `Referenced from:` / `dyld[` notes are skipped; indented progress lines stay). Stamp file = commit last installed; a `mkdir` lock so one build runs; the build runs in its own process group (`set -m`) so Stop kills every child; build functions are never called inside `&&`/`||` (there `set -e` is silently ignored). Install by moving the bundle (old one moved aside first, then deleted: one copy only). A build made while the app runs (`--build`) is kept with its commit as the next install, so the next click with the app quit installs it at once instead of building again. The launcher is signed with the same Developer ID as the app, so after the first install macOS lets it replace the app without the App Management grant.
- **Here:** `scripts/fork/app.sh`, `scripts/fork/launcher.swift`, `scripts/fork/install-dock-app.sh` (compiles to `~/Applications/OpenBot Launcher.app`, bundle id `com.eliasx45.openbot-fork.launcher`, pins it once). State and log in `build/fork-launcher/`.
- **Check:** quit OpenBot, make a commit, click: builds, installs, opens. Click again with no new commit: opens at once. With OpenBot open: `scripts/fork/app.sh --build`, quit, click: installs in a second.

## 3. Fast launcher builds: this Mac only, no timestamp, patch what changed

- **Get:** full build ~1¾ min (103 s measured, 2026-11-03); a commit that only changes the app's JavaScript or resources ~40 s (measured by hand on a clone: electron-vite 7 s, unsigned electron-builder 28 s, swap 1.3 s, sign 3.4 s, verify 0.9 s); a docs-only commit builds nothing. Of upstream's last 60 commits, 37 patch, 18 full, 5 nothing.
- **Why:** Codync lessons (its entry 5): universal builds, slow release profiles and per-file timestamp calls made rebuilds 5½ min.
- **How (portable):** build only the machine's architecture (`--arm64`). Nothing native compiles here (voice runtime, remote desktop runtime and Cua driver are pinned downloads that each skip when present), so no LTO profile to override. Sign without a secure timestamp (`-c.mac.timestamp=none`). `bun install` only when the lockfile, a `package.json` or a patch changed (hash stamp). Diff the installed commit against the new one and sort each path by what it is compiled into: `src/`, `packages/`, the Vite config, `scripts/agent-runtime-lock*` (imported by `src/main`) → the asar; `resources/` → plain files in Resources and the asar (`src/` imports `resources/agent-import/*/SKILL.md?raw` and `resources/plugin-catalog/catalog.json`); tests and e2e/smoke scripts, docs, other apps (mobile, API, bots), CI, lint tooling (`tools/`) and the launcher → nothing; dependencies, runtime locks, `electron-builder.yml`, the fork entitlements and anything unknown → full build. A patch clones the installed app (APFS `cp -Rc`, instant), swaps in `app.asar`, `app.asar.unpacked` (its native addon re-signed) and the `Info.plist` that carries the asar hash (`ElectronAsarIntegrity`, from an unsigned electron-builder run with the same flags), re-signs the outer bundle and checks `codesign --verify --deep --strict`; any failure falls back to a full build.
- **Here:** `changes`, `patch`, `steps`, `install_deps` in `scripts/fork/app.sh`.
- **Check:** `build/fork-launcher/build.log`: first line names the parts (`full`, `( js)`, `( res js)`, `none`), last lines `built in N s` and `installed`.

## 4. Signed with Elias's Developer ID: macOS permissions survive rebuilds

- **Get:** Screen Recording, Accessibility, Microphone and Automation are granted once and stay granted across rebuilds.
- **Why:** ad-hoc or unsigned builds look like a new app to macOS each build, so grants vanished (Codync lesson, its entry 6).
- **How (portable):** sign every build with one stable certificate. `codesign` gets the full name `Developer ID Application: mohamed elias hamadouche (GQQBT37P3D)` (the short name is ambiguous: an Apple Distribution certificate has it too); electron-builder refuses the prefix (`Please remove prefix "Developer ID Application:"`) and wants the short name, picking the Developer ID certificate itself, hardened runtime, the app's entitlements; no notarizing. Drop entitlements that need the original team's provisioning profile (`com.apple.developer.associated-domains`, `com.apple.developer.team-identifier`): without the profile macOS refuses to start an app that claims them. Set `ElectronTeamID` to the new team. Nested binaries signed by a third party (Cua driver) keep their own signature. Grants made for the original signature (team `ZTRDTUL87R`) must be removed (−) and granted again once; the keychain item "OpenBot Safe Storage" asks once ("Always Allow").
- **Here:** `identity`, `entitlements`, `builder_flags` in `scripts/fork/app.sh`; `scripts/fork/entitlements.mac.plist`.
- **Check:** `codesign -dv /Applications/OpenBot.app` shows `TeamIdentifier=GQQBT37P3D`; after a rebuild Computer Use still works without a new prompt.

## 5. Same app identity and data as the release, with a rollback

- **Get:** the fork opens Elias's existing data, agents (Rasta, Booty, Shelf) and settings; the official release can be put back.
- **Why:** the fork replaces the installed release in place.
- **How (portable):** keep the bundle id (`app.openbot.desktop`) and product name, so a packaged run's userData stays `~/Library/Application Support/OpenBot` and the agent workspaces stay in `~/OpenBot`. Before the first install over a build signed by another team, zip that app (`ditto -c -k --keepParent`) and copy its database with `sqlite3 .backup` (upstream `main` migrates the schema forward; an older release refuses a newer database).
- **Here:** `backup_official` in `scripts/fork/app.sh` → `build/official-<version>.zip`, `build/official-<version>-openbot.db`. Rollback steps in [README.md](README.md#data-signature-rollback).
- **Check:** after the first install the agents and chats are there; both backup files exist.

## 6. The `$` list shows the agent's own skills and commands

- **Get:** typing `$` in an agent's box lists, after OpenBot's skills and `~/.agents/skills`, every skill its CLI loads: for Claude all of `~/.claude/skills` (editing-harvest, effectcraft-motion…, ~84 with a `SKILL.md`), the `.claude/skills` of its project folders, and, once a session of the agent started, what Claude itself says it has: plugin skills (`figma:figma-use`, `voicemode:converse`…) and Claude Code's built-in commands (`compact`, `context`, `init`, `review`…, badge **Command**); for an ACP agent (Codex ACP, Gemini, OpenCode…) the commands it lists itself. MCP servers stay in the list. Picking a skill makes the agent use it; picking a command as the first thing in the message runs it (`$compact keep the API notes` = `/compact keep the API notes`).
- **Why:** the box said "This agent has no skills" though Claude agents load all 113 of Elias's skills (Codync lesson, its entry 10 / ADR 0007).
- **How (portable):** list per agent, on request, what the engine itself has: its skill folders in the user's home (provider's skill folders, `CLAUDE_CONFIG_DIR` for Claude) and in each project folder, plus the agent's last command list (kept in memory per agent; a change makes the open lists read again): an ACP agent's `session/update` `available_commands_update` (it arrives outside turns too, so read it before the "is a turn active" check), and for Claude, which runs on the Agent SDK and sends no ACP update, the query's `supportedCommands()` at each session start (also after an idle release), filtered again at `system/init` (its `terminal_slash_commands`) and replaced by `system/commands_changed`. Left out of Claude's list, as claude-agent-acp does: `clear cost keybindings-help login logout mcp output-style:new release-notes todos`, terminal-only commands, and the `agents:` / `openbot:` plugin skills (OpenBot's own, already listed). Disk skills come first, so they show before the first session; names already listed are left out. A skill's tag id is `agent:<name>`; the provider reads it as `/<name> (skill)`: Claude Code runs a skill the user names as `/<name>` with its Skill tool, and ACP agents know their commands by that name. A Claude Code built-in command (`SlashCommand.builtin`) is `agent-cmd:<name>` and reaches the provider as a bare `/<name>` (no " (skill)", which Claude would read as arguments); at the very start of the message, with the blank before it dropped, Claude Code runs it, and OpenBot's Claude client already sends a message that starts with `/` without its memory/teammate blocks. Elsewhere in the text it stays words for the model. So built-ins stay in `$` (decided from the code): a plain user message reaches `turn/start` unwrapped; a reply-to, a teammate message or a handoff wraps the text, and then the command does not run.
- **Here:** `src/backend/fork-agent-skills.ts` (`claudeCommandsForList`, `expandAgentCommandTags`); `listInstalledForChatTags` in `src/main/skill-marketplace-service.ts` (last constructor argument from `application-services.ts`); `available_commands_update` in `#sessionUpdate` of `src/backend/acp-client.ts`, and `#forkEmitCommands` in `src/backend/claude-client.ts` (after `#startThread`, `init` / `commands_changed` in `#handleMessage`) → `openbot/agentCommands/updated` → `agentCommands` in `src/backend/agent-service.ts`; tag text in `displayMessageReferences` of `src/backend/agent/delivery-content.ts`; `AGENT_COMMAND_ID_PREFIX` in `packages/contracts/src/ipc-skills.ts`; badge in `pickerOptionBadge` (`packages/ui/src/features/conversation/composer-picker.ts`, icon `SquareSlash`, i18n `composer.picker.badge.command`, English only).
- **Not done:** the command list is in memory only, so after an OpenBot restart plugin skills and built-ins come back with the agent's first session; a built-in later in the text does not run; a user skill named like a built-in hides the built-in in the list (Claude runs the built-in).
- **Check:** in Shelf's box type `$edit`: editing-harvest, editing-cut… appear (badge Workspace, place `~/.claude/skills/…`). Pick editing-harvest, send "what does this skill do": Shelf calls its Skill tool for editing-harvest. After one message to Shelf, `$figma` lists `figma:figma-use`… and `$comp` lists `compact` with badge Command. Send `$compact` alone: the chat shows the compaction (context bar drops), no "(skill)" answer.

## 7. Waits: an agent sleeps until something is done, then carries on in the same chat

- **Get:** an agent can say "wake me when this render is written / this process exits / that agent finishes / this URL answers", end its turn, and get woken in the same chat and provider session, knowing everything it knew. The wait shows above the composer (upstream's open-waits block) with Cancel; a macOS notification when it ends; the wake shows in the chat as a routine-style marker "⏳ Wait over: <note>".
- **Why:** long EffectCraft renders made agents poll (tokens) or stop and forget. Upstream 0.59/main has waits (`await_event`), but only a routine run or a script event wakes them: the agent must make a routine and a detached script. Codync lesson (its entry 3 / ADR 0004): plain code watches, the wake goes to the existing session.
- **How (portable):** tool `wait_until {note, file+settleSeconds | pid | agentId | url, timeoutMinutes ≤ 1440}`, exactly one condition; it returns at once and the agent ends its turn. The wait is an ordinary open wait (so `list_waits` lists it and `close_wait` or the user's Cancel cancels it, with no wake); what is watched goes to a JSON file next to the database, so waits survive a restart. Every 2 s plain code checks: file exists and `size:mtime` unchanged for `settleSeconds` (a file already there must change first), `kill(pid, 0)` fails, the other agent was busy (a turn or a queued message) and now is not (idle at the start means its next work), the URL answers < 500 (checked every 10 s). On fire or timeout: the wait is closed, a notification, and a delivery with a routine sender (`routineId` `fork-wait`, no real routine) is queued to the agent's own chat; its text is the whole prompt ("[OpenBot: ⏳ wait over] … not a message from the user", note, what was watched, result, the request it continues). A routine run never wakes a watched wait. Refused in channel/messaging threads, like `await_event`.
- **Here:** `src/backend/agent-waits/fork-wait-conditions.ts` (`ForkWaitConditions`); routed from `AgentWaits.handleTool` (`useConditions`, filter in `wakeForRun`); built in `src/backend/agent-service.ts` (wake via `RoutineScheduler.enqueueHandoff`, boot-recovery `quietRoutineDelivery` exception, `forkNotify` from `src/main/application-services.ts`); tool in `src/backend/openbot-tools.ts`; prompt line in `developer-instructions.ts`; wake text in `deliveryPromptInput` (`delivery-content.ts`). File: `~/Library/Application Support/OpenBot/fork-wait-conditions.json`.
- **Not done:** no separate `cancel_wait` (upstream's `close_wait` cancels); the card is upstream's open-waits block, not a card in the timeline; no wait by process name.
- **Check:** tell an agent "the secret word is heron; wait_until the file /tmp/heron.txt, then tell me the word"; it ends its turn and the wait shows above the box. `echo hi > /tmp/heron.txt`: within ~7 s a notification, "⏳ Wait over" in the chat, and the agent says "heron". A second wait cancelled with its Cancel: no wake.

## 8. Project folder as the agent's home ("Work here")

- **Get:** in an agent's Settings › Folders, each added folder has **Work here** (the Workspace row too, to go back). The agent's sessions then start in that folder, so Claude loads the project's `CLAUDE.md`, `.claude/skills`, `.claude/settings*.json` and hooks, as when you run `claude` there. The agent's own folder (`~/OpenBot/Agents/<id>`) stays its home for OpenBot's files.
- **Why:** agents always started in `~/OpenBot/Agents/<id>` and got project folders only as extra directories, so Shelf needed an AGENTS.md line "cd into motion-kit first and follow its CLAUDE.md". Codync's bots have a working folder.
- **How (portable):** an optional `workFolder` on the agent, which must be one of its added folders (removing that folder, or a folder that is gone, falls back to the workspace). The session's `cwd` is the work folder on start, resume, each turn and history reads; the writable roots stay the same (they include it). Changing it restarts the agent's sessions like a folder change. Because the CLI no longer sees the agent's own instruction file, that file's text goes into the prompt, and the prompt says "you work in the project folder X; your own folder is Y". Claude resumes a session only from its cwd's project folder (`~/.claude/projects/<sanitized cwd>/<id>.jsonl`), so before a resume the transcript is copied there when it is elsewhere: the same session goes on, with its memory.
- **Here:** `agentSessionCwd` in `src/backend/agent/workspace-sandbox.ts`, used in `thread-lifecycle.ts` (`#startParams`, `threadParams`, `#instructionsFile`), `drain-scheduler.ts` (`turn/start`), `boot-recovery.ts`; `workFolder` in `AgentSummary` (`packages/contracts/src/ipc-agents.ts`), `src/backend/agent-store.ts` (update, read, copy), `standingProfileChanged` (`profile-save.ts`), prompt line in `developer-instructions.ts`; `carryClaudeTranscript` (`claude-history.ts`, called from `#startThread` in `claude-client.ts`); IPC `agent:folders:work-folder` (`setAgentWorkFolder`: contracts, preload, `agent-folder-handlers.ts`, `setWorkFolder` in `src/main/agent-folders.ts`, preview mock); UI `FolderRow` / `AgentFoldersPage` in `packages/ui/src/features/conversation/AgentFolders.tsx`, i18n `agentSettings.folders.workHere*` (English only).
- **Not done:** project `.mcp.json` servers still don't load (upstream's `strictMcpConfig`: OpenBot's MCP panel is the only door); local agents only (not on a joined server); other providers get the cwd but their transcript move isn't handled.
- **Check:** Shelf › Settings › Folders › Add folder… `/Users/elias/Developer/motion-kit` › Work here. Ask Shelf "what is your cwd, and what does your CLAUDE.md say?": `/Users/elias/Developer/motion-kit` and the motion-kit rules; it still remembers the earlier chat. Then remove the "Workspace: … cd into it first" line from `~/OpenBot/Agents/agent-7c6c0058-…/AGENTS.md`.

## 9. Claude Code's MCP servers in the MCP panel ("From Claude Code")

- **Get:** the MCP servers panel lists every user-level server of Claude Code (`~/.claude.json` `mcpServers`: cua, figcraft-app, hindsight, linear, motion-library, motion-library-remote, pencil, quickshotx, reelscope) with a **From Claude Code** badge and "Edit in ~/.claude.json". All agents get them (Claude, Codex and the ACP providers read the same list). No Edit or Remove; the switch works and stays as set. Test and Sign in (linear) work.
- **Why:** OpenBot starts Claude with `strictMcpConfig: true` ("the MCP panel is the only door"), so agents saw none of Elias's Claude Code servers, and retyping them would drift.
- **How (portable):** keep the panel as the one list and add the mirrored servers to what it lists, not to its table. Each read of the list stats `~/.claude.json` (`$CLAUDE_CONFIG_DIR/.claude.json` when set) and converts the top-level `mcpServers` again when its mtime or size changed: `stdio` → command/args/env, `http` → url/headers; `sse` and other types are skipped (the panel has no SSE client). Each entry goes through the panel's own normalize/validate; a bad one is skipped and logged by name only. Ids are `claude-code-<name>` (hand-made rows are `mcp-<uuid>`), which is what makes them read-only: save and remove refuse them ("This MCP server comes from Claude Code. Edit it in ~/.claude.json."). A hand-made row with the same name wins: the mirrored one is left out and logged. The list stays within the panel's 32 servers. Env values and headers are never written anywhere by OpenBot: they live in memory and are registered for log redaction like stored rows. The on/off switch is kept by name in `fork-claude-code-mcp-off.json` beside `openbot.db`. A `fs.watchFile` poll (3 s, stat only, not persistent) re-reads the file; when the `mcpServers` result changes, every agent gets a fresh provider session at its next turn, as after a panel save. `~/.claude.json` is only read, never written. Project `.mcp.json`, `projects.<path>.mcpServers` and plugin servers are left out.
- **Here:** `src/backend/fork-claude-code-mcp.ts` (`ClaudeCodeMcpMirror`); `list`, `get`, `save`, `remove`, `setEnabled`, `watchClaudeCode` in `src/backend/mcp-server-store.ts`; `watchClaudeCode` / `close` in `src/backend/agent/mcp-gateway.ts`; constructed in `src/backend/agent-service.ts`, watch started in the "restore channel links" startup step; `CLAUDE_CODE_MCP_SERVER_ID_PREFIX` / `isClaudeCodeMcpServerId` in `packages/contracts/src/ipc-mcp-servers.ts`; badge, note and menu without Edit/Remove in `src/renderer/src/features/servers/ServerMcpPanel.tsx`; i18n `mcp.panel.fromClaudeCode*`, `error.backend.mcpServerFromClaudeCode` (English only).
- **Not done:** `${VAR}` expansion in values (none of Elias's entries use it); the open panel does not refresh by itself after a `~/.claude.json` change (reopen it).
- **Check:** Server settings › MCP servers: the 9 servers with **From Claude Code**; the ⋯ menu has only Test (and Sign in for linear). Switch hindsight off, quit and reopen OpenBot: still off. Ask an agent "which MCP tools do you have?": cua, reelscope… are listed. Add a server to `~/.claude.json` with `claude mcp add -s user …`: the next turn of an agent has it; reopen the panel to see it.

## Checked, not needed

- **Several agents use the computer at once (Codync entry 9 / ADR 0006):** OpenBot has no lock between agents. Each provider starts its own `cua-driver mcp` proxy on the shared daemon (`src/main/cua-driver-runtime.ts`), and the action tap (`src/main/cua-driver-action-tap.ts`) only watches calls for the rim and cursor; it refuses and delays nothing. So several agents can already work at once, in different apps or the same one (no "another agent is using this app" guard). The only rule: an agent's task threads get no Computer Use, so one agent's own chat holds its screen work (`#sessionAgent` in `thread-lifecycle.ts`). Checked 2026-11-03; skipped. If two agents clashing in one app becomes a problem, Codync's per-app hold (look-only free, `pid` + background holds that app 20 s, foreground/untargeted holds all) would go in the tap's `data` handler, which sees each call's `name` and `args`.
